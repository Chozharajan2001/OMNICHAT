# ADR-001: AES-256-GCM for API Key Encryption

## Status
Accepted

## Context
OmniChat needs to encrypt user-provided API keys (BYOK - Bring Your Own Key) before storing them in the database. The encryption must be:
- Authenticated to detect tampering
- Efficient enough for frequent encryption/decryption operations
- Available in the server-side Node.js runtime; the vault is not a browser Web Crypto implementation

## Decision
Use AES-256-GCM (Galois/Counter Mode) for encrypting API keys.

### Implementation Details
- **Algorithm**: AES-256-GCM via Node.js `crypto`
- **Key Size**: 256 bits (32 bytes)
- **IV Size**: 128 bits (16 bytes), generated with `crypto.randomBytes(16)` for each encryption
- **Authentication Tag**: 128 bits (16 bytes), generated by GCM
- **Key Derivation**: SHA-256 of the UTF-8 `ENCRYPTION_SECRET_KEY` value produces the 32-byte key. Missing secrets and values shorter than 32 characters are rejected; use a high-entropy secret, not a password.
- **Wire Format**: `iv:ciphertext:authTag`, with each component separately hex-encoded, not concatenated into one hex string. The format contract is exactly three even-length hex fields: IV and tag are each 32 hex characters; ciphertext may be empty.

### Code and Callers
- [Vault](../../src/lib/crypto/vault.ts): `encryptApiKey` serializes the encrypted value; `decryptApiKey` verifies the GCM tag before returning plaintext. Strict input validation must preserve the existing format and SHA-256 derivation.
- [API-key queries](../../src/lib/db/queries/api-keys.ts): `saveApiKey` encrypts before storage. `getDecryptedKey` decrypts for server-side use; on decryption failure it marks the record invalid and returns `null`. Key listings return metadata, not plaintext or ciphertext.
- [API-key POST](../../src/app/api/api-keys/route.ts) saves keys; [chat POST](../../src/app/api/chat/route.ts) retrieves the decrypted key for provider requests.

## Consequences

### Positive
- **Authenticated Encryption**: GCM provides confidentiality and integrity when the key remains secret and IVs are not reused
- **Performance**: AES-GCM can benefit from hardware acceleration
- **Standard**: GCM is specified in NIST SP 800-38D; algorithm standardization is not an independent audit or a production-readiness assessment of this implementation
- **No Padding**: GCM does not require block padding

### Negative
- **IV Reuse**: Must never reuse an IV with the same key; random generation reduces collision risk but does not guarantee uniqueness
- **Key Management**: Requires secure storage of the environment secret. Changing it makes existing records unreadable unless they are re-encrypted; the vault has no automatic key rotation or key versioning.
- **Runtime**: This implementation depends on Node.js `crypto`, not browser APIs

### Security Limits
- **Tampering**: GCM authentication rejects altered ciphertext or tags that fail verification
- **Replay Attacks**: IV uniqueness does not prevent replay of a previously valid encrypted value; the vault tracks no freshness or replay state
- **Key Compromise**: IV uniqueness does not protect against master-key compromise. The same derived key protects all records; compromise exposes every API key encrypted under it.
- **Record Binding**: No authenticated additional data binds ciphertext to a user or provider; encryption alone does not prevent substitution of a valid encrypted value between records

## Alternatives Considered

### AES-256-CBC
- **Rejected**: Requires separate HMAC for authentication, more complex
- **Padding Oracle**: Unauthenticated CBC can expose padding-oracle attacks

### ChaCha20-Poly1305
- **Not Selected**: Another authenticated-encryption option; relative performance depends on hardware and implementation

### Plain AES (no authentication)
- **Rejected**: No integrity checking, vulnerable to tampering
