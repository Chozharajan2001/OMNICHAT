# ADR-001: AES-256-GCM for API Key Encryption

## Status
Accepted

## Context
OmniChat needs to encrypt user-provided API keys (BYOK - Bring Your Own Key) before storing them in the database. The encryption must be:
- Secure against known cryptographic attacks
- Efficient enough for frequent encryption/decryption operations
- Compatible with browser environments (for desktop app)
- Authenticated to detect tampering

## Decision
Use AES-256-GCM (Galois/Counter Mode) for encrypting API keys.

### Implementation Details
- **Algorithm**: AES-256-GCM
- **Key Size**: 256 bits (32 bytes)
- **IV Size**: 96 bits (12 bytes) - randomly generated per encryption
- **Authentication Tag**: 128 bits (16 bytes) - automatically generated by GCM
- **Key Derivation**: Master key from environment variable (ENCRYPTION_KEY)

### Code Example
```typescript
import { createCipheriv, createDecipheriv, randomBytes } from 'crypto';

function encrypt(plaintext: string, masterKey: Buffer): string {
  const iv = randomBytes(12); // 96-bit IV
  const cipher = createCipheriv('aes-256-gcm', masterKey, iv);
  const encrypted = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]);
  const tag = cipher.getAuthTag(); // 128-bit authentication tag
  return Buffer.concat([iv, encrypted, tag]).toString('hex');
}
```

## Consequences

### Positive
- **Authenticated Encryption**: GCM provides both confidentiality and integrity
- **Tamper Detection**: Authentication tag detects any modification
- **Performance**: GCM is hardware-accelerated on modern CPUs
- **Standard**: NIST-approved, widely used and audited
- **No Padding**: Stream cipher mode, no padding oracle attacks

### Negative
- **IV Reuse**: Must never reuse IV with same key (mitigated by random generation)
- **Key Management**: Requires secure storage of master key (environment variable)
- **Browser Compatibility**: Requires Web Crypto API or Node.js crypto module

### Risks Mitigated
- **Tampering**: GCM authentication tag detects modifications
- **Replay Attacks**: IV uniqueness prevents replay
- **Key Compromise**: Master key separation limits exposure

## Alternatives Considered

### AES-256-CBC
- **Rejected**: Requires separate HMAC for authentication, more complex
- **Padding Oracle**: Vulnerable without proper padding validation

### ChaCha20-Poly1305
- **Rejected**: Less hardware acceleration, slower on x86_64
- **Good for**: ARM processors, but not our primary target

### Plain AES (no authentication)
- **Rejected**: No integrity checking, vulnerable to tampering
